## Goal

让**三线表**（只有横线、没有竖线，`find_tables()` 一格都识别不出来的那种）
里的译文也被拦在**行内**，不再往下"借"走相邻行的空间。

## Architecture

阶段 3 已经建好了"约束框"这条链路（`paragraph.constraint_bbox` →
`_clamp_to_box()` 收紧 `max_height`）。本阶段**不新增机制**，只给这条链路
补一个**新的框来源**：

```
layout.table_cells(page)   PyMuPDF find_tables()      → 单元格（有列边界，更精确）
layout.table_rows(page)    页面横线两两成行（本项目）    → 行带（只有上下边界）   ← 新增
        ↓  layout.constraint_for(bbox, cells, rows)   ← 唯一的绑定 owner（单元格优先）
paragraph.constraint_bbox + constraint_kind
        ↓
typesetter._clamp_to_box()  只收紧、不放大（下限=段落原框）
```

**为什么行带够用**：约束作用在**阅读方向（叠放轴）**上，也就是"别往下压到
下一行"。横排的叠放轴就是纵向，行带给出的下边界正是需要的那条。
（竖排的叠放轴是横向，行带给不出列宽，因此不受益 —— 这一点如实写在文档里。）

**为什么复用而不是新写一套**：约束的语义（只收紧、下限卡原框、双模式共用）
已经由阶段 3 定死在 `_clamp_to_box()` 一处。再写一套"行约束"必然与之分叉。

### Task 4.2 — layout：抽出线条读取 + 横线切行

```python
def _rule_segments(page, min_len_ratio=0.06):
    """取出够长的直线段，分成 (横线, 竖线)。`table_regions` 与 `table_rows` 共用。"""

def _merge_rules(horizontals, y_tol=RULE_Y_TOL):
    """横线按 y 聚类成行边界（同一条线常被画好几遍，不聚类会切出零高度的假行）。"""

def table_rows(page, min_rules=3, min_len_ratio=0.06, min_height=ROW_MIN_HEIGHT):
    """只用横线切出的行带 [(x0, y0, x1, y1), ...]。"""
    horizontals, _ = _rule_segments(page, min_len_ratio)
    if len(horizontals) < min_rules:
        return []
    boundaries = _merge_rules(horizontals)
    rows = []
    for upper, lower in zip(boundaries, boundaries[1:]):
        if lower[1] - upper[1] < min_height:
            continue
        rows.append((min(upper[0], lower[0]), float(upper[1]),
                     max(upper[2], lower[2]), float(lower[1])))
    return rows
```

**为什么 `row_for` 在多条都套住时取最扁的一条**：行带是从整页横线两两切出来的，
"表 1 的底边到表 2 的顶边"这种跨表空档也可能套住一段正文。取最扁的更符合
"这一段属于哪一行"的直觉；而且就算选错，后果只是"少借了点空间"，
不会把段落压到比原框更小（有下限保护）。

### Task 4.3 — 统一绑定入口 + 命名正名

```python
def constraint_for(bbox, cells, rows):
    """返回 (框, 来源)，来源为 'cell' / 'row' / ''。单元格优先（多了列边界）。"""
```

`Paragraph.cell_bbox` 改名为 **`constraint_bbox`**，并新增 `constraint_kind`。
理由（名实分离）：这个框现在有两种来源，继续叫 `cell_bbox` 就是名不副实；
而且两个来源各有一个开关，"这一段是被哪条机制约束的"是必须能查到的事实。

### Task 4.4 — 按来源分开关 + 统计拆分

```python
def _constraint_enabled(paragraph, cell_clamp, row_clamp) -> bool:
    kind = getattr(paragraph, "constraint_kind", "")
    if kind == "cell":
        return cell_clamp
    if kind == "row":
        return row_clamp
    return False
```

统计拆成 `clamped_cell` / `clamped_row` 两个计数：合在一起会把两条机制的功劳
混成一件事，出问题时也看不出是哪条在动。

### Task 4.5 — 修掉排版统计不透出的缺陷

`pipeline._typeset()` 原先只把 `verify_*` 与 `outputs` 合并进 `task.stats`，
`typeset_document()` 返回的排版统计**从未透出**。后果是阶段 3 的验证脚本
`stats.get("cell_clamped", 0)` 一直读到默认值 0，于是得出了
**"单元格约束在真实文档上一次都没生效"这个错误结论**并写进了设计文档。

修法：`task.stats = {**task.stats, f"typeset_{mode}": {…全部排版统计…}}`。

**这一步的代码量比功能本身还小，但它才是这一阶段最重要的修复** ——
没有它，前面所有"实测"都可能是假的。

### Task 4.6 — 测试与真实文档复核

`tests/test_cell_clamp.py` 第 4 节从"退化路径行为不变"改造成"三线表按横线切行"：
