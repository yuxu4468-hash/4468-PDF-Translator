## 1. 背景：实测到的真实现状

以下数据来自 `work/design/` 下的诊断脚本，对 46 份语料实测。

### 1.1 公式几乎没有结构保护

| 分类 | 段数 |
| --- | --- |
| 普通正文 | 15014 |
| 被判"代码/公式/非文本"但不像公式 | 1888（绝大多数是纯数字单元格，跳过是**正确**的） |
| **像公式但被送去翻译** | **1304** |
| 真正被 `looks_like_code` 拦下的 | **24** |

即：18000 余段里 `looks_like_code` 只触发 24 次，**等于不触发**。公式保护目前
完全依赖提示词里的"保留数字、公式、变量名"，没有任何结构校验。

### 1.2 数学符号会渲染成豆腐块

**关键修正**：全部 63 个测试符号都**不属于 CJK 区段**，因此在真实排版路径里
由 `FontPair` 路由到**内置拉丁字体（Helvetica / Times）**，而不是中文字体。

- 内置 Helvetica / Times 覆盖：**40 / 63**
- **真实缺失 23 个**：`∛ ∓ ⋅ ∘ ∇ ‱ ⁻ ⁺ ⁰ ⇒ ⇔ ⊆ ∠ ⊥ ∥ ∅ ₀ ₁ ₂ ₃ ₄ ↗ ↘`
- 这 23 个**都能在本机字体里找到落点**（MS Gothic / Yu Gothic / Microsoft JhengHei /
  Malgun Gothic / Microsoft YaHei）

`sanitize_for_font()` 只丢弃**私有使用区**字符；非私有区缺字形会被原样保留，
绘制成 notdef —— 画面是空白方块，提取出来是空。所以这 23 个符号属于**静默损坏**。

### 1.3 表格只有区域级识别

`layout.table_regions()` 只能给出"这一片是表格"，没有任何单元格概念。实测：

| 指标 | 数值 |
| --- | --- |
| `page.find_tables()` 有单元格的页 | **25 / 36** |
| 识别出的单元格总数 | 2463 |
| 段落中心落入某个单元格 | 275 |
| **未落入任何单元格** | **129（命中率 68%）** |

**结论：网格路径覆盖不全，退化路径才是主力。** 三线表（只有横线，无竖线）上
`find_tables()` 完全失效（例：DGHT瑞士分会 23 页表格，识别出 0 个单元格）。

### 1.4 数值失配的实测率（阶段 1 完成后回填）

`work/design/measure_numeric.py --fresh`（全新缓存、强制重译，测首次翻译的真实水平）
在三份真实文档上实测：

| 文档 | 待校验段 | 初检失配 | 重试修正 | 最终回退 | token |
| --- | --- | --- | --- | --- | --- |
| DGHT_无尾目(蛙类)饲养准则_德文 | 474 | 0 | 0 | 0 | 53572 |
| DGHT瑞士分会_爬行动物饲养最低要求 | 956 | 0 | 0 | 0 | 46025 |
| 德国联邦BMEL_爬行动物饲养最低要求专家意见_1997 | 1267 | 8 | 7 | 1 | 111112 |
| **合计** | **2697** | **8（0.30%）** | **7** | **1** | 210709 |

三条结论直接决定后面的做法：

1. **失配率很低（0.30%），且集中在表格/公式密集的那一份文档**（BMEL 1997）。
   这不是"模型普遍会改数字"，而是"数字密集处才会出错"——所以**事后校验 + 定向重试
   这套低成本方案是对的**，不需要事前改提示词或上结构化翻译。
2. **一次定向重试能修掉 7/8**，成本极低（只在失配时多发一个小批次）。
3. 那 1 段修不好的，经查是**误判**：原文 `0,75 x 0, 5 x 0,75 über 1,5 m`
   里 `0, 5` 的空格是 PDF 提取产物，严格读法把源数字读成 `0` 和 `5`，于是译文的
   `0.5` 对不上。已加入"严格失败后再做一次宽松判定"（`_reglue_numbers`）修掉这一
   误判——**误判的代价是把一段正确译文退回原文，是本功能最该避免的后果**。

**遗留**：其余 46 份语料未逐一实测。抽样三份的失配率 0.30% 是否代表整体，属于
待观察项；统计口径已就位（`numeric_mismatched` / `numeric_rejected`），
批量跑一遍即可得到全量数字。

### 1.5 真正会丢符号的地方是**竖排**（阶段 2 完成后回填）

阶段 2 落地后，对全库 46 份做了符号扫描，挑出"内置字体缺字形"的符号最密的一份
（`DGHT鳄类工作组_鳄类最低饲养要求(23页).pdf`，265 个公式符号、其中 **22 个
`∅`**）做 A/B 出片复核，发现一件设计阶段没预料到的事：

| 事实 | 数据 |
| --- | --- |
| 这 22 个 `∅` 全部出现在**旋转 -90° 的竖排表格单元格**里 | 22/22 |
| `∅`(U+2205) 在**内置 Helvetica 与中文字体里都没有字形** | `has_glyph` 均为 0 |
| 横排路径的落点字体（MS Gothic）能画它 | 所以横排根本不是问题所在 |
| 竖排只能用一个字体 → 只能走等价写法 | 修复前输出 `empty 1.6 m` |

也就是说：**降级链第 2 步（换本机字体）救不了竖排**，而这份文档里唯一的
真实损失恰好全在竖排。设计 §4.2 把"ASCII 等价"写成最后兜底，实际上它在竖排里
是**唯一**手段 —— 这一点在计划里已写明，但当时低估了它的比重。

由此改进了等价写法的取值方式：**形近字优先，ASCII 拼写兜底**。
`∅` 在德语技术文档里是**直径**符号（`∅ 1,6 m`），写成 `empty` 会把"直径 1.6 米"
变成"空的 1.6 米" —— 这正是"兜底也要讲语义"的例子。`Ø` 形近且常见，
实测微软雅黑/等线都有该字形，于是修复后输出 `Ø 1.6 m`。

同样处理了 `∑→Σ`、`∏→Π`（希腊字母形近字比 `sum`/`prod` 更贴近原貌）。
<br>表的结构因此从"符号 → 字符串"改成"符号 → **候选序列**"，
逐个取第一个当前字体真能渲染的候选。

### 1.6 阶段 3 的第一次结论是**错的**，必须记下来

阶段 3 落地后做 A/B 出片复核，统计显示 `cell_clamped` 全为 0，于是我在设计文档里
写下结论：**"单元格约束在这两份真实文档上一次都没收紧过"**。这个结论是错的。

真相：`typeset_document()` 返回的排版统计**从来没有被 pipeline 透出到
`task.stats`**（只把 `verify_*` 与 `outputs` 合并了进去）。验证脚本
`stats.get("cell_clamped", 0)` 取的是一个**不存在的键**，`.get` 的默认值 0
被当成了测量结果 —— 典型的"静默降级被当成事实"。

修掉数据链路（`task.stats["typeset_<mode>"]` 透出全部排版统计）之后，同一份文档
同一份缓存重新出片（三份文档，`work/design/verify_stages.py --tables --rules`）：

| 文档 | 绑定到单元格 | 绑定到表格行 | 实际收紧（格/行） | 越出单元格 | 越出表格行 | 排版溢出 | 产物体积 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| DGHT瑞士分会_爬行动物饲养最低要求(26页) | 213 | 928 | **0 / 330** | 41 → 41 | 108 → **90** | 0 → 0 | 不变 |
| DGHT_无尾目(蛙类)饲养准则_德文 | 219 | 240 | **26 / 23** | 7 → 6 | 31 → **25** | 2 → 2 | 不变 |
| DGHT鳄类工作组_鳄类最低饲养要求(23页) | 648 | 409 | 0 / 0 | 18 → 18 | 19 → 19 | 0 → 0 | 不变 |

**修正后的结论**：单元格约束**并非从不生效**——蛙类那份实际收紧了 26 段；
加上表格行约束，三份文档一共收紧 379 段，越出表格框的段落减少 24 段，
产物体积与排版溢出都没有变差。鳄类那份 0 段是正常的：它的表格行里下一行
紧接着有文字，`_available_below()` 本来就比框边界更紧，取 `min()` 没有差别。

**教训**（写进文档，因为它比功能本身更重要）：**"读到 0"和"没读到"必须区分开**。
统计类结论必须确认键真的存在（`"key" in stats`），否则 `.get(key, 0)` 会
把"没透出"伪装成"没生效"。这正是本项目"名实分离"原则要防的东西 ——
而这次是我自己踩的。

### 1.7 三线表按横线切行：做完之后（阶段 4）

**为什么做**：阶段 3 只覆盖 `find_tables()` 认得出来的网格（68%），而三线表
（只有横线）**一格都识别不出来**（实测 323 页里 0 个格）—— 恰恰是这类表格在
语料里占多数。横线本来就是行边界，`table_regions()` 也早就在读它们了。

**动手前先量**（`work/design/probe_rows.py`，全库 46 份）：

| 指标 | 数值 |
| --- | --- |
| 能按横线切行的页 | 160 |
| 切出的行带总数 | 893 |
| 落在行带里的可翻译段落 | 2679 |
| 其中**行边界比原机制更紧** | **801（29.9%）** |
| 最极端的收紧幅度 | 443.9pt → 16.0pt |

**做完之后实测**（A/B 出片，只翻 `table_row_clamp`）：见上表 —— 瑞士分会那 23 页
三线表收紧 330 段、越界少 18 段；蛙类那份行约束收紧 23 段、越界少 6 段。

**已知边界（如实记录）**：

- 行带只给**上下**边界、不给**列**边界。所以它只能约束"别往下压到下一行"，
  对竖排段落（叠放轴是横向）基本无用 —— 那需要列宽，是 T2 的事。
- 收紧后仍有段落越出表格框（瑞士分会 90 段、蛙类 25 段）：一部分是
  `min_font_size`（默认 5pt）这个硬下限导致的"缩到底也放不下"，一部分是原段落框
  本身就压在框边界上。日志里 `overflow` 计数会如实报出来。
- 鳄类那份一格一行都不收紧：不是没生效，是它的框边界本来就不是更紧的那个。

**仍然没做的**（按性价比排序，待定夺）：

1. **单元格/行矩形参与绘制框构造**（T2）：直接解决剩余越界，但要先解决
   "识别歪了怎么办"，需要更谨慎的兜底策略。
2. **公式符号保护（P2）**：与数值保护同构 —— 源文里有、译文里没有的符号
   也做一次定向重试。暂不做：实测这批文档里模型并没有丢符号，没有实测缺口
   就先不造机制。

## 2. 目标与非目标

### 目标

1. 译文里的**数字、单位、比例、条款号**与原文一致；不一致时不得静默进入成品。
2. 译文里的数学符号**不再出现空白方块**。
3. 表格单元格内的译文**不越出所属单元格、不压到相邻单元格**。

### 非目标（明确不做）

- 不重绘表格线、不做列宽自适应（那是 T2，本期明确不做）
- 不做 LaTeX / MathML 公式渲染
- 不做数学表达式的语义识别与重排
- 不修改任何原始矢量图形
- 不引入需要下载的字体（M2 留作后续可选项）

## 4. 设计

### 4.1 数值/单位保护（P1：事后校验 + 定向重试）

**位置**：`src/core/translator.py`，在 `_apply()` 落盘译文之前。

**新增纯函数**（放在 `src/shared/text_utils.py`，不新建模块）：

```
extract_numbers(text) -> list[str]              # 归一化后的数值多重集
missing_numbers(source, target) -> list[str]    # 源有、译文里找不到的数值
```

**指纹定义：只比数字，不比单位。**

| 归一化规则 | 说明 |
| --- | --- |
| `\d+(?:[.,]\d+)*` 抽取数值 | 覆盖整数、小数、千分位 |
| `,` 与 `.` 视为等价 | 德语小数逗号 `1,5` 与中文 `1.5` 是同一个数 |
| 去掉千分位分隔 | `1.000` 与 `1000` 等价（按上下文无法完全区分，取宽松） |
| `x` / `×` / `*` 统一为 `x` | `5 x 1` 与 `5×1` 等价 |
| `-` / `–` / `—` / `~` 统一 | 区间写法差异不算失配 |
| **中文数字转阿拉伯数字**（见下） | `二十五` 与 `25` 等价 |

**中文数字比对（按用户决定加入）**

德语/英语原文用阿拉伯数字，中文译文可能写成汉字数字，所以**译文侧**要把中文数字
归一成阿拉伯数字再比对：

```
十三 → 13     二十五 → 25     两百 → 200     三千五百 → 3500
第五 → 5（"第" 前缀特判）      第 3 条 → 3
```

**只在译文侧做这个转换**，且**保守**——只转换"独立成词的数词串"：
数词串必须被非汉字字符（空白、标点、外来词）或句首/句尾界定。

这样设计的理由，是利用了**单向包含**的一个好性质：

- 译侧多转换出一个数字**无害**（判定不检查译文多出来的数值），
  所以 "第五" 这类转换漏了顶多不帮忙，不会造成误判；
- 反过来，如果在汉字词组内部乱转（`一般`→`1般`、`十分`→`10分`），
  会**凭空造出**原文没有的数字，反而可能掩盖真正的漏译。
  所以词组内的数词一律不转，这是刻意的。

已知代价：`第五` 这类带前缀的能转，但嵌在词组里的（`一般`、`一定`）不转。
若原文含 `1` 而译文只写了 `一般`，会被判失配并触发重试——属于**宁可多问一次**。


**刻意不比较单位与条款号前缀**：

- 单位会**跨语言改写**（`50 cm` → `50 厘米`），比较单位必然误报；
  单位在原文里的语义价值已经由"数字必须保留"覆盖。
- 条款号同理（`§7` → `第 7 条`），只取其中的数字即可。

**判定：单向包含，不做对称比较。**

源文本里的每个数值，都必须在译文中找到。**不检查译文多出来的数值。**

这一条是被真实案例逼出来的：

- 反例（必须抓到）：`Essen, 1. Juni 2018` → `埃森，2018 年` —— 源里的 `1` 和 `6`（Juni）
  在译文中消失，判定失配 ✓
- 正例（不能误报）：`Essen, 1. Juni 2018` → `埃森，2018年6月1日` —— 数字 `6` 是
  **月份名词转成数字**带来的新增，属于正常翻译，不得判为失配 ✓

若改成对称比较，第二种正确译文会被误杀——这是本设计里最容易做错的一处。

**处理流程**：

```
一批翻译返回
  → 逐段 missing_numbers()
     ├ 为空            → 直接采用
     └ 非空            → 收集失配段，发起**一次单独的小批次重试**
                         （只含失配段，不重发整批）
                         重试时在 system prompt 追加：
                         "以下数字必须原样保留，一个字符都不能改：<数值列表>"
                         → 再比对
                            ├ 为空   → 采用重试结果
                            └ 非空   → 清空该段 target（回退原文）
                                        + task.log 告警
                                        + 计入 stats["numeric_rejected"]
```

**"回退原文"的确切含义**（按用户决定）：把该段的 `target` 清空。排版阶段对
`target` 为空的段落**既不擦除也不绘制**，所以原段落保持德文原样留在页面上——
与本项目既有的"取不到译文就保留原文"行为完全一致，也不影响回读校验
（校验只检查有 `target` 的段落）。


**失配明细只报一次**（按用户决定）：明细按 `(原文片段, 缺失数值)` 去重，
**每个文档最多输出前 5 条**，同一任务内不重复输出。
统计数字 `numeric_rejected` 照常累加，不受此限制。

理由：46 份资料批量跑下来，同一个失配模式（例如表格数值行）可能触发几百次，
逐段刷屏会让日志失去可读性；而统计数字仍然完整，不影响判断。

**成本**：只在失配时才产生额外请求。一致的情况下零额外开销。

### 4.2 数学符号字形降级（M1）

**位置**：`src/core/typesetter.py` 的 `FontPair`。

**降级链**（逐字符，前一步命中即止）：

1. 当前路由字体（CJK 字符→中文字体；其余→内置拉丁字体）
2. **本机字体中第一个含该字形的字体**（由 `fonts.resolve_symbol_face(code)` 提供，
   结果按字符缓存；只嵌入用到的字形，`subset_fonts()` 会把它压到极小）
3. **ASCII 等价写法**（查表 `SYMBOL_ASCII_FALLBACK`，已备好 63 条）
4. 仍无 → 丢弃该字符并在日志告警（保持现有 `sanitize_for_font` 的语义）

ASCII 等价示例：`≤→<=`、`≥→>=`、`≠→!=`、`×→x`、`÷→/`、`²→^2`、`₀→_0`、
`∑→sum`、`√→sqrt`、`°→deg`、`→→->`

**为什么不只用 ASCII 等价**：保留原符号的原貌保真度更高（尤其 `°`、`×`、`≤`）。
先尽量保住原字符，等价写法只作最后兜底。

**新增字体查询**（`src/core/fonts.py`）：

```
resolve_symbol_face(code) -> fitz.Font | None
```

按码位缓存；只在第 2 步真正需要时才遍历候选字体（惰性，不拖慢常规排版）。

### 4.3 表格单元格内约束（T1）

**位置**：`src/core/pdf_parser.py`（识别并存格子）+ `src/core/typesetter.py`（约束）。

**数据**：

- `Paragraph.cell_bbox: tuple | None` —— 该段所属单元格（无则 None）
- `PageInfo.cells: list` —— 该页所有单元格（供后续扩展，本期只读）

**识别**（两段式）：

1. **网格路径**：`page.find_tables()` → 单元格矩形列表；段落中心落入某格则绑定。
   实测覆盖 25/36 页、68% 段落。
2. **退化路径**：未绑定到格的段落，沿用**现有**的障碍物机制
   （`_available_below` / `_overlaps_any`）。这条路径今天已经在跑，不新增机制。

**约束**（仅 `mono` 嵌字模式）：

```
若 paragraph.cell_bbox 存在：
    max_height = min(现有 max_height, cell_bbox.y1 - original.y0)
    # 即：可用高度同时受"下一段上沿"和"本格下边界"约束，取更紧的
否则：
    维持现状
```

**竖排段落**同样适用：此时约束作用在 bbox 的**宽**方向（叠放轴），
即 `stack_room = min(现有, cell_bbox.x1 - original.x0)`。

**不改变**：擦除矩形、绘制方式、字体选择。本项只收紧可用高度上限。

**实施时的两点修正（已落地，如实记录）**：

1. **约束对 mono 与 dual 一并生效**。原设计写"仅 mono"，但 `max_height` 在进入
   模式分支**之前**就已算好、两种模式共用；dual 的向下扩展同样会压到下一行，
   一并收紧正是想要的效果。（若只对 mono 生效，需要在分支内各算一次。）
2. **下限卡在"段落自己原来的框"**：`max_height = max(原框高, min(现值, 到格边距离))`。
   原文本身就占着这么大，压到它以下既解决不了问题又会把正常段落改小；
   万一某段被错误地绑到一个偏小的格子上，压下去就是**误改**。
   宁可漏检不可误改 —— 约束只能收回借来的空间。

**已知限制（本阶段未做）**：三线表的**横线**挡不住译文。`find_tables()` 识别不出
单元格，退化路径只避让相邻段落的**文字**，因此译文可能越过横线（实测合成三线表
下沿越过横线 3.5pt，但停在下一段文字之上）。彻底解决需要"按横线切行"这一**新机制**，
不在本期范围内；是否要做，等这批能力落地后再按需评估。

## 6. 风险与回滚

| 风险 | 应对 |
| --- | --- |
| 数值校验**误报** | 三重防线：① 归一化吃掉 `,`/`.`、`x`/`×`、`-`/`–` 的写法差异；② **单向包含**（不查译文多出来的数字），避免"月份名词转数字"被误杀；③ 开关 `numeric_guard` 可整体关闭 |
| 单向包含**漏报**改写 | 已知代价：源 `5` 被改成 `10` 时，若 `5` 恰好还在别处出现则检不出。实测语料里数字重复出现的情况少，接受此代价换取低误报 |
| 重试导致成本上升 | 只对失配段重试，且**每段最多 1 次**；统计里可观测重试次数 |
| ASCII 等价破坏了原符号观感 | 降级链第 2 步（保留原符号）优先于第 3 步 |
| 第 2 步引入额外字体使产物体积上升 | `subset_fonts()` 只保留用到的字形；实测验收产物体积增量 |
| `find_tables()` 在三线表上失效 | 退化路径复用现有机制，不新增；A5 专门测这条 |
| 单元格约束过紧导致字号被压得过小 | 保留现有 `min_font_size` 下限与 `overflow` 统计；不越格优先于字号 |

**回滚**：四个能力各由独立开关控制（`numeric_guard` / `symbol_fallback` /
`table_cell_clamp` / `table_row_clamp`），出问题可单独关闭而不影响其余功能。

## 7. 已决与未决

### 已决（用户确认）

| 项 | 决定 |
| --- | --- |
| 数值失配的兜底 | **回退原文 + 告警**（清空 `target`，原段保持德文） |
| 中文数字 | **参与比对**——译文侧把独立成词的汉字数词归一成阿拉伯数字 |
| 失配明细输出 | **只显示一次**——按 `(原文片段, 缺失数值)` 去重，每文档最多 5 条 |
| 失配明细是否另导出机器可读清单 | **暂不导出**（阶段 1 实测后决定）。实测失配率 0.30%、单文档最多 8 段，明细已进日志（落盘）与 `task.stats`，再加一个 JSON 产物没有实际用武之地。若将来批量跑全量语料后发现明细不够用，再补 —— 届时有 `numeric_mismatched` 这个现成的判据。 |
| 等价写法的取值 | **形近字优先，ASCII 拼写兜底**（阶段 2 实测后决定）。`∅`→`Ø` 而非 `empty`（该文档里 `∅` 是直径符号）；`∑`→`Σ`、`∏`→`Π` 同理。表值由字符串改为候选序列。 |
| 表格单元格约束是否只对 mono 生效 | **两种模式都生效**（实施时修正）。`max_height` 在进入模式分支前就已算好、两模式共用；dual 的向下扩展同样会压到下一行。 |
| 三线表是否按横线切行 | **做**（用户选定）。横线本来就是行边界；实测 801/2679 段的行边界比原机制更紧，做完后三线表文档收紧 330 段、越界少 18 段。 |
| 行的约束是否与单元格共用一个开关 | **不共用**。`table_cell_clamp`（PyMuPDF 启发式）与 `table_row_clamp`（本项目自己的启发式）出问题的方式不同，必须能分开回滚。 |
| 排版统计怎么给到调用方 | **进 `task.stats["typeset_<mode>"]`**，不只打日志。日志会轮转、会被 `MAX_LOG_LINES` 截断；"生效了没有"必须能被程序读到 —— 这条是被一次真实误判换来的（见 §1.6）。 |

### 未决

1. `find_tables()` 需要 PyMuPDF ≥ 1.23；本项目锁定 1.27.2.3，无需额外处理。

## 8. 实施顺序建议

1. **P1 数值保护**（最小、立刻受益，并能**顺带测出真实失配率**，为后续决策提供数据）
