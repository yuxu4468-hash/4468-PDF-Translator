## 它是什么

把一份英文（或日文、韩文等）PDF 丢进来，选好大模型，点一下按钮，
得到一份**中文（或其它目标语言）的 PDF**，正文位置、字号、配色、图片、
表格线基本保持原样。

与常见方案的区别：

| 方案 | 问题 |
| --- | --- |
| 复制到翻译网站 | 丢掉版式，图表全没了，长文档极难读 |
| 扫描 + OCR + 重新排版 | 依赖 PyTorch / PaddleOCR，动辄几个 GB，启动慢 |
| 通用机器翻译 API | 不理解上下文，术语前后不一致，学术文本质量差 |
| **本项目** | 直接读 PDF 文本层，交给大模型按段落翻译，再写回原坐标，**依赖只有 3 个库** |

## 核心特性

- **轻量**：核心只依赖 `PyMuPDF` + `Flask` + `requests`，无 PyTorch / Paddle。
  译文用本机已装的中文字体渲染（自动匹配，见下），找不到就退回 MuPDF 内置 CJK 字体，
  连字体文件都不用准备。OCR 是可选模块，只多用已经装好的 `onnxruntime`。
- **支持扫描版 PDF**：内置 OCR，用 PP-OCR 的 ONNX 模型识别没有文本层的扫描件 /
  影印件，识别完照常翻译并回填，还能把原图上的外文一并遮盖掉。
- **嵌字（版式还原）**：擦掉原文、在**原来的基线与行距**上写译文，并保持字体风格 ——
  衬线配衬线、加粗配**真实粗体字重**、字号能不改就不改、译文偏短时拉字距填满原行宽、
  中英交界加间隙、中文标点遵守避头尾禁则。图片与矢量图形（表格线、图表）完整保留。
  产出看起来就是"原来那份文档变成了中文"。
- **版面分析**：自动识别**双栏 / 三栏**排版并按正确顺序阅读；识别页眉、页脚、
  页码、水印并默认跳过；能把被 PDF 生成器拆散成"一行一块"的段落重新合并；
  能把"加粗小标题 + 正文"同处一个文本框的块按行级风格拆开，让标题拿回粗体。
- **两种模式**：`嵌字版`（原位替换，默认）与 `双语对照`（原文+译文并列）。
- **批量 + 并发**：一个请求翻译多段，多批并行，请求数比"一段一请求"少一个数量级。
- **省钱**：按 服务商/模型/目标语言/提示词/术语表/原文 做译文缓存，重跑同一文档不重复计费。
- **术语表**：强制统一专有名词，`Transformer=变换器` 这样逐行填写即可。
- **多格式产出**：嵌字 PDF、双语 PDF、Markdown 对照稿、纯译文 TXT、分段对照 JSON。
- **可换模型**：DeepSeek / 硅基流动 / OpenAI / Kimi / 智谱 / 通义 / 本地 Ollama /
  任意 OpenAI 兼容接口，甚至内置一个不联网的"模拟翻译"用于验证流程。

## 快速开始

### 1. 准备环境

需要 **Python 3.9 或更高版本**（开发与测试环境为 3.11）。

```bat
pip install -r requirements.txt
```

### 2. 启动

双击 **`启动.bat`**（会自动检查依赖并打开浏览器），或者命令行：

```bat
python -m src.main
```

然后在浏览器里访问 **http://127.0.0.1:8765/**（会自动打开）。

### 3. 使用

1. 把 PDF **拖进左侧的上传区**，等待解析完成；
2. 在「翻译设置」里选择服务商、填入 **API Key**（默认预选了 DeepSeek），
   点「测试连接」确认能通；
3. 选择**目标语言**与**翻译模式**，必要时填**术语表**；
4. 点「开始翻译」，进度条、阶段和日志会实时刷新；
5. 翻译完成后在右侧预览译文页面，在「结果文件」里下载。

> **API Key 存在哪？** 首次启动时程序会按 `config/config.example.json`
> 在 `config/config.json` 生成配置（**该文件已在 `.gitignore` 里，不会进仓库**）。
> Key 只写在本机这个文件里，不上传、不外发；界面里也能改。

> **想先不花钱试试？** 把服务商切到「**模拟翻译（仅调试）**」，
> 它会本地生成假译文，几秒钟就能跑完整流程，用来确认 PDF 解析与排版效果是否满意。

### 命令行参数

```bat
python -m src.main --port 9000      :: 换端口（默认 8765，被占用会自动顺延）
python -m src.main --no-browser     :: 不自动打开浏览器
python -m src.main --debug          :: 开发模式（热重载）
```

## OCR：翻译扫描版 PDF

扫描件、影印件、图片导出的 PDF **没有文本层**，直接翻译会得到空结果。
打开 OCR 后，程序会把这类页面渲染成图片、识别出文字，再照常走翻译与回填流程。

### 它怎么工作

```
扫描页 --渲染(DPI)--> PP-OCR 检测文本框 --> 识别每一行 --> 按行距聚合成段落
      --> 交给大模型翻译 --> 回填排版（先遮盖原图上的外文，再写译文）
```

几点值得说明的设计：

- **不新增任何 Python 依赖**：直接在本机已有的 `onnxruntime` 上跑 PP-OCR 的 ONNX 模型，
  刻意绕开了 opencv（本机那份 `cv2` 安装是坏的）和 pyclipper ——
  检测后处理用 `scipy.ndimage` 做连通域分析，识别用 numpy 自己实现 CTC 解码。
- **模型按需下载**：模型放在项目内的 `models/ocr/`，带 SHA256 校验，可离线复用，
  不往系统目录里塞东西。
- **扫描页自动判定**：**没有文本层 + 图片覆盖页面**才算扫描页，
  所以普通电子版 PDF 不会白白走一遍 OCR（`auto` 模式）。
- **遮盖原文**：扫描件的文字是图像像素，删不掉，所以排版时会先用采样到的背景色
  画一块矩形盖住它，再写译文；深色底、彩色底的扫描件也能正确还原。
- **按语言选模型**：中英混排（默认）/ 英文 / 日文 / 韩文 / 拉丁语系 / 西里尔 /
  阿拉伯语 / 泰语 / 希腊语 / 天城文。

### 怎么用

**第一步：装依赖**（只有两个，`启动.bat` 也会自动帮你装）

```bat
pip install onnxruntime numpy
```

**第二步：下载模型**（默认语言约 21 MB，只需一次）

```bat
python -m src.main --download-ocr ch        :: ch / en / japan / korean / latin ...
python -m src.main --download-ocr all       :: 下载全部语言
python -m src.main --ocr-status             :: 查看已下载哪些
```

也可以直接在界面里点「下载模型」，或者在首次翻译扫描件时自动下载。

**第三步：正常用**。上传扫描件 → 在「OCR 扫描件识别」里确认模式为**自动**、
语言为**中英混排** → 开始翻译。

界面里还有一个「**在这一页试识别**」按钮：选一页点一下，就能看到这一页识别出
多少行、每行的置信度、以及它判定为扫描页的理由 —— 换语言、调 DPI 之前先用它
确认效果最省事。

### OCR 相关配置

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| `ocr_mode` | `auto` | `off` 关闭 / `auto` 只处理扫描页 / `always` 所有页都 OCR |
| `ocr_lang` | `ch` | 识别语言，决定用哪个模型 |
| `ocr_dpi` | `300` | 页面渲染精度。低质量扫描件可提到 300；越低越快 |
| `ocr_min_confidence` | `0.5` | 置信度下限，低于此值的识别结果丢弃 |
| `ocr_det_version` | `v5` | 文本检测模型版本，`v4` 更小 |
| `ocr_use_cls` | `false` | 是否判断文本行方向（0°/180°），扫描件歪斜时有用 |

### 精度实测

用一份模拟扫描件（中英德混排、含变音符号、数字、网址、邮箱）实测：

| 模型 | 识别结果 | 耗时 |
| --- | --- | --- |
| `ch`（PP-OCRv5，默认） | 6/6 行完全正确，置信度 0.97~1.00 | 0.4s / 页 |
| `ch_v4`（PP-OCRv4） | 6/6 行正确，个别破折号识别为汉字 | 0.21s / 页 |
| `en`（纯英文模型） | 英文正确，中文全部识别失败 | 0.21s / 页 |

一页 A4 大约 0.4~0.7 秒，CPU 即可，不需要显卡。

### DPI 怎么选

默认 **300 DPI**，这是实测出来的甜点。用一份「9pt 小字压在彩色照片上」的折页
图鉴（比普通文档难得多）做对比：

| DPI | 效果 |
| --- | --- |
| 200 | 小字行会被**整行漏检**（`(Pelophylax esculentus)` 只认出 `lentus)`） |
| **300** | 同一行**完整正确**认出，耗时反而更短（图像更清晰、碎框更少） |
| 400 | 与 300 接近，但图像更大、内存占用更高 |

也就是说：**提高 DPI 在这个场景下既更准又不更慢**，所以默认就设成 300。
只有处理超大页面或内存紧张时，才考虑降到 200。

另外，检测模型在文字压照片时会把一行切成几段。程序会判断**两段之间的空隙里
到底有没有墨迹**（比对灰度对比度）：有墨迹就说明中间那截只是没被检测出来，
于是把整行合并后再识别 —— 这正是上表中 300 DPI 能救回整行的原因。

## 两种翻译模式

### 嵌字版 / 仅译文（`mono`）—— **默认**，推荐

擦掉原文，在**原来的位置、原来的基线上**写入译文。
产出的 PDF 看起来就像"原来那份文档变成了中文"：版式、图片、插图、表格线
（矢量图形）全部原样保留，只有文字被换掉。

适用于：只关心译文、需要打印或提交、或者要求"看起来就是原始文档"的场合。

#### 为了"看起来就是原文"，嵌字模式具体做了什么

| 能力 | 说明 |
|---|---|
| **字体风格匹配** | 读原 PDF 的字体名，衬线配衬线（宋体一类）、无衬线配无衬线（黑体一类）、**加粗配真实粗体字重** |
| **基线锚定** | 首行落在原文首行的基线（`span.origin.y`）上，而不是段落框顶边 —— 否则字号一变就会整体上下漂移 |
| **原文行距网格** | 多行段落沿用原文相邻基线的中位间距，译文的行落在原来那几行上 |
| **字号保真** | 能在原字号下放下就**不改字号**，放不下才按需二分收缩（实测某份折页 55 段里 44 段保持了原字号） |
| **字距拉伸** | 译文比原文短时把行内字距拉开填满原行宽（上限可配），避免右边空一大块 |
| **中英间隙** | 汉字与拉丁字母交界处加 0.25em 间隙（参考 UTR #59） |
| **中文禁则** | 句读点号、闭括号不允许出现在行首（用"标点悬挂"处理）；开括号不允许出现在行末 |
| **拉丁字符独立字体** | 见下方"为什么要给拉丁字符单独用字体" |
| **粗体小标题还原** | 加粗小标题与正文排进同一个文本框时，按行级风格把它们拆开，标题才能拿回粗体与自己的基线 |

#### 关于字体：会自动选，也可以自己指定

译文用哪个中文字体由**原文风格 → 本机字体**自动匹配，无需下载任何东西：

```
原文 Calibri（无衬线/常规）  →  等线 DengXian（无衬线/常规）
原文 Calibri-Bold（粗体）    →  等线 Bold（真实粗体字重）
原文 Times（衬线）           →  宋体 SimSun
```

挑选时会逐项**实测**每个候选字库，按优先级排除掉不适合的：

| 探测项 | 排除什么 | 实测反例 |
| --- | --- | --- |
| `subset_safe` | CFF/OTF 字库（`subset_fonts()` 会静默失败，产出从几十 KB 膨胀到好几 MB） | Noto Sans SC 的 `.otf` 版 → 7.3 MB |
| `variable` | 可变字体（MuPDF 只取第一个命名实例） | `NotoSansSC-VF` 被解析成 `Thin`（极细） |
| `valid_codepoint` | 画不出中文的字体 | — |
| `cjk_ok` | 会把汉字提取成 **CJK 兼容表意文字**的字库（复制/搜索对不上） | 思源宋体 Heavy 66 个字、Noto Sans SC 107 个字 |
| `simplified_coverage` | **简体汉字覆盖不全**的日文/韩文字体 | Malgun Gothic 仅 11%、MS Gothic 20% |
| `space_ok` | 空格会被反查成 `U+00A0`（NBSP）的字库 | 微软雅黑、Noto Sans SC |
| `ascii_ok` | 会改变 ASCII 码位的字库 —— **只对竖排段落致命**（那条路径只能用单一字体） | 等线把 `-` 变成 `U+2010` |
| `light` | 细体（Light/Thin 是独立字重，不是"常规"） | 微软雅黑 Light |

其中 `cjk_ok`、`simplified_coverage`、`ascii_ok` 排位都在**字重和衬线之前** ——
字符正确性是正确性问题，字重和风格只是观感问题。

> ⚠️ 简体覆盖度这一项是踩过坑才加的：一度为了 ASCII 安全而选中了
> Malgun Gothic（韩文字体），它数字好看但只有 11% 的简体字，
> 缺字被画成 notdef、提取为空，一份 75 页文档因此"丢"了 130 段窄表头。

想用自己的字体：在界面的「嵌字字体」里填字体文件路径，或改配置项
`lettering_font_regular` / `lettering_font_bold`。

> **为什么要给拉丁字符单独用字体**
>
> 译文里的 `Vipera berus`、`Baden-Württemberg`、`2020` 这些拉丁片段，
> **不走中文字体，走内置的 Helvetica / Times**。原因有两个：
>
> 1. **观感**：CJK 字库里的拉丁字形按全角设计，又宽又呆，混排会显得松散。
> 2. **正确性**（更要紧）：不少 CJK 字库把多个 Unicode 码位映射到同一个字形，
>    MuPDF 生成 ToUnicode 反查表时会挑错一个，后果不是"看着不对"，而是
>    从产出 PDF 里**复制 / 搜索文字时对不上**。实测：
>
>    - 微软雅黑 / Noto Sans SC：空格 → `U+00A0`（NBSP），搜 `"Vipera berus"` 搜不到；
>    - 等线 / Noto Sans SC / 思源宋体：连字符 → `U+2010`，搜 `"Baden-Württemberg"` 搜不到；
>    - 微软雅黑 Light：括号 → `U+FE3E`/`U+FE3F`。
>
>    内置的 Helvetica / Times 系列**没有这个问题**（ASCII 往返 100% 正确），
>    而且它们是 base-14 字体：不嵌入、不占体积。这也是 PDFMathTranslate（pdf2zh）
>    与 BabelDOC 的做法。

### 双语对照（`dual`）—— 用于校对与学习

保留原文，译文紧跟在每一段**下方**（若原文是倒排文字，则排在其**上方**，
因为倒排文字的阅读方向是自下而上的）。

实现方式不是简单地"往下塞"，而是：

1. 计算该段落沿阅读方向到下一个段落之间的可用空白；
2. 在这块空间里，把**原文（沿用原来的断行）+ 分隔线 + 译文**作为一个整体，
   **二分搜索最大的可用字号**；
3. 空间不够就整体缩小字号（下限可配，默认 5pt）。

**两条硬保证**：

- **绝不重叠**：如果扩展后的区域会压到相邻段落（紧凑排版里相邻行的 bbox
  本来就互相咬合），该段会自动**退化为"仅译文"**——内容完整、不重叠，
  只是这一小段没保留原文。日志里会告诉你有多少段是这样处理的。
- **绝不漏译**：每份产出都会回读校验一遍，确认每段译文都真的写进了 PDF，
  有缺失会在日志里明确报出来。

因此紧凑版面下的代价是字号会变小、个别段落退化为单语。
**图片画册、折页、图鉴这类版面非常紧的文档，建议直接用「嵌字版」。**

## 工作原理

```
PDF ──► 解析 ──► 版面分析 ──► 可翻译性筛选 ──► 大模型翻译 ──► 排版回填 ──► 导出
```

**1. 解析（`core/pdf_parser.py`）**
用 `PyMuPDF` 的 `get_text("dict")` 取出文本块 / 行 / span，连同坐标、字号、
字体、颜色、书写方向一起转成中间表示（`core/models.py`）。

**1b. OCR（`core/ocr/`，仅扫描页）**
页面没有文本层但有图片覆盖时，渲染成位图交给 PP-OCR：DBNet 检测文本框
（`scipy.ndimage` 连通域 + 外扩），CRNN + CTC 识别每一行，再按行距把行聚合成段落，
坐标换算回 PDF 点后作为普通段落并入文档。

**2. 版面分析（`core/layout.py`）**

- **阅读顺序**：对 x 方向做"覆盖计数投影"，覆盖度最低处就是栏缝；据此把块分成
  左栏 / 右栏 / 通栏（`spanning`）三类，左栏读完再读右栏，通栏块按其 y 位置插入。
  页眉、页脚、页码参与整页顺序但不归属任何一栏。三栏及以上递归处理。
  分栏判据还要求两侧块**纵向高度重叠 ≥45%**，避免把单栏文档误判成双栏。
  探测不到栏缝时退回经典的 XY-cut。
- **段落合并**：部分 PDF 把每行导出成独立块。若上一段末行顶到栏右边界、下一段
  首行从栏左边界开始、行距小于 0.85 倍字号且字号颜色一致，则合并为一段。
- **页眉页脚 / 页码**：先按页面上下 8% 区域初筛，再统计跨页重复率确认
  （出现页数 ≥35% 才认定为页眉页脚），避免把正文里偶尔重复的句子误删。
- **对齐方式**：由各行左右边界与中心线推断 左 / 居中 / 右 / 两端对齐。

**3. 可翻译性筛选（`pdf_parser.mark_translatable`）**
过滤纯数字/符号、URL、邮箱、代码片段，以及**已经是目标语言**的段落，省 token。

**4. 大模型翻译（`core/translator.py`）**

- 把多段文本打包成一个 JSON 数组 `[{"i":1,"t":"..."}]` 发出去，要求模型返回同序号的
  译文数组 —— 一次请求搞定十几段。
- **四级容错解析**：标准 JSON → 正则提取 `{"i":..,"t":".."}` → 编号行 → 顺序对齐。
  仍然缺项就缩小批次重试，最后逐条单独请求，尽最大努力不丢内容。
- 超长段落按句子切分后分别翻译再拼回。
- 批次之间用线程池并发（并发数可配）。
- 以内容哈希为键做译文缓存，重跑不再计费。
- 自动把关卡生成器拆散的段落、术语表、文档开头作为上下文提示一并送给模型。

**5. 排版回填 / 嵌字（`core/typesetter.py` + `core/fonts.py`）**

- **文本度量自己做**：用 `fitz.Font.text_length` 按"中日韩字符可任意断行、拉丁单词
  整体不断行、超长 URL 按字符硬切"的规则折行并算高度，因此"放不放得下"在绘制前
  就已知，可以**二分搜索最佳字号**，而不是靠 `insert_textbox` 的返回值反复试。
- **擦除用 `apply_redactions`，并且 `images=NONE, graphics=NONE`** —— 只删文字，
  **图片和表格线（矢量图）原样保留**。
- **填充色从页面渲染图采样**得到，深色 / 彩色背景也能正确还原；若该处色彩杂乱
  （说明文字压在图片上），则不填充，避免把插图遮住。
- **擦除矩形会避开"保留原文"的邻居**：`apply_redactions` 删的是与该矩形**相交**的
  全部文字，而紧凑版式里相邻段落的 bbox 常因字体升降部留白互相咬合（实测折页上有
  3~4pt 纵向重叠）。不收边就会把邻居整行静默删掉。
- **字体匹配（`core/fonts.py`）**：本机字体探测（Windows 注册表 / macOS / Linux
  字体目录）→ 按"原文风格（衬线/粗体）→ 字库特性"排序 → 选出中文字体。
  排序优先级的依据全部来自实测，见 `core/fonts.py` 的模块文档。
- **字体对（CJK + 拉丁）**：汉字用匹配出的中文字体，拉丁字符用内置 Helvetica /
  Times（base-14，不嵌入、不占体积、ASCII 往返 100% 正确）。
- **基线锚定**：首行基线取原文首个 span 的 `origin.y`（实测与 `insert_text`
  的基线参数完全一致），而不是段落 bbox 顶边 —— 用顶边会因字号变化整体上下漂移。
- **原文行距网格**：多行段落用原文相邻基线的中位间距作为行距，
  并在 `[自然行高, 自然行距×1.8]` 之间夹紧，既不会叠字也不会过空。
- **中文禁则（避头尾）**：句读点号/闭括号不允许落在行首（用"标点悬挂"处理，
  最多超出一个字宽）；开括号/前引号不允许落在行末。
- **字距拉伸**：译文比原文短时把行内字距拉开填满原行宽（上限 `lettering_tracking`）。
  只对左对齐/两端对齐的行做，最后一行不拉，空档超过行宽 30% 也放弃。
- **中英间隙**：汉字与拉丁字母交界处加 0.25em（参考 UTR #59）。
- **数学符号字形降级**：译文里的 `≤ ≥ × ° √ ∑ ∛ ₁₀ ↗` 这类符号，若当前字体
  没有字形（内置 Helvetica 对实测 63 个公式符号覆盖 40 个），先去本机字体里找
  一个有该字形的来画 —— 保留原符号是首选；本机也找不到才换成 ASCII 等价写法
  （`≤` → `<=`、`°` → `deg`）。不这样做，缺字形的符号会**静默**画成空白方块，
  从产出里提取出来是空。竖排文字走 `insert_textbox`（只能用单一字体），
  所以那一路只能靠 ASCII 兜底。
- **表格约束框**：译文不许越出所属的表格框，避免压到相邻单元格/行。
  两种来源，单元格优先（多了列边界，更精确）：
  1. **单元格** —— 用 `find_tables()` 取；实测只覆盖 68% 的表格段落，
     三线表（只有横线）上一格都识别不出来。
  2. **表格行** —— 用页面上的**横线**两两切出行带。实测全库 46 份：
     能切行 160 页 / 893 条行带，落在行带里的可翻译段落 2679 段，
     其中 801 段（29.9%）的行边界比原有机制更紧，最极端的几段原来能
     "借"到 443pt（半页）。
  两者都识别不到时沿用原有的"按相邻段落算可用空间"机制，行为不变。
- 用 `TextWriter` 按基线逐行写出，位置完全可控。

**6. 导出（`core/exporter.py`）**
嵌字 PDF、双语 Markdown、纯译文 TXT、分段对照 JSON。
保存前调用 `subset_fonts()` 做字体子集化 —— 不这样做，内嵌的中文字库会让
输出 PDF 从 30 KB 膨胀到 1.7 MB。
**子集化失败是静默的**（CFF 字库只在 stderr 打一行 `MuPDF error`，不抛异常），
所以排版阶段会检查产出体积，异常偏大时给出可操作的提示。

**7. 产出校验（`core/pipeline.py`）**
每份 PDF 保存后都**回读**再核对两件事：

- **译文是否真的写进去了**：排版库在极端情况下会"静默不写"
  （`insert_textbox` 放不下时返回负数且一个字符不画；`TextWriter` 遇到缺字形
  只画空白方块，提取出来是 `\x00`）。比对时只看"文字骨架"（字母数字与汉字），
  忽略标点与字体替换带来的差异，避免误报。
- **不该删的原文是否还在**：没有译文的段落（页眉页脚、代码、取不到译文的段落）
  必须原样保留在页面上。

## 测试

```bat
python tests\run_all.py            :: 全部离线测试（不需联网、不花钱）
python tests\run_all.py --ocr      :: 额外跑 OCR 测试（需已下载模型）
python tests\run_all.py --real     :: 额外跑真实大模型测试
```

也可以在真实 API 上单独跑：

```bat
set PDFT_REAL_API_KEY=sk-xxxx
python tests\test_real_api.py
```

测试覆盖：

- **全链路**：双栏/三栏阅读顺序、页眉页脚页码识别、段落合并、翻译、排版、导出；
- **版式几何**：译后 PDF 是否越界、是否有文字重叠、是否有过小字号；
- **不丢内容**：逐段回读产出文件，确认每段译文都真的写进了 PDF（含 180° 倒排回归）；
- **接口集成**：上传 → 信息 → 预览 → 翻译 → 轮询 → 结果 → 下载 → 译文预览，
  含目录穿越防护与配置字段白名单；
- **前端契约**：JS 引用的 DOM id 与后端接口是否真实存在，静态分析抓拼写不一致；
- **OCR**：构造真正的"无文本层 PDF"，验证扫描页判定、识别准确率、
  段落聚合、遮盖原文、整条流水线；
- **真实模型**：把一段论文摘要交给 DeepSeek 翻译，校验译文以中文为主、
  专有名词保留、编号列表格式完好。

## 常见问题

**Q：一定要联网吗？**
云端模型要联网；也可以用「本地 Ollama」完全离线，或者用「模拟翻译」验证流程。

**Q：扫描版 PDF（图片型）能翻译吗？**
能，但需要先启用 OCR（见上文「OCR：翻译扫描版 PDF」）。
装好 `onnxruntime` + 下载模型后，界面里把「OCR 模式」设为**自动**即可。
如果提示"未发现可提取的文本"却又没走 OCR，通常是：模型没下载、语言选错了
（例如法文扫描件选了纯中文模型），或者页面既没文字也没图片。

**Q：OCR 识别得准吗？**
对清晰的扫描件（200 DPI 以上、正常字体）中文与英文准确率很高。
模糊、倾斜、手写、艺术字会明显下降。建议先用界面上的「在这一页试识别」
看实际效果，必要时把 DPI 调到 300、或换用对应的语言模型。
识别不准会直接影响翻译质量 —— 重要文件请务必校对。

**Q：OCR 会不会拖慢普通 PDF？**
不会。默认 `auto` 模式只对**没有文本层**的页面才跑 OCR，
电子版 PDF 完全不受影响，也不会加载模型。

**Q：翻译中途关掉网页会怎样？**
任务在服务端后台线程里跑，关掉网页不影响；重新打开页面会从 `localStorage`
恢复任务 id 并继续显示进度。但**关掉命令行窗口 / 服务进程**会中断任务。

**Q：为什么双语模式下有些字变小了？**
版面太紧凑，放不下原文+译文，程序按既定规则统一缩小到能放下的字号。
日志里会提示有多少段触发了缩小。建议这种文档用「仅译文」模式。

**Q：提示「API Key 无效」/「无法连接」？**
先在界面上点「测试连接」，它会给出中文的具体原因（401 / 404 / 429 / 超时 /
DNS 等）。常见原因是密钥填错、模型名写错、账户余额不足或所选服务商网络不通。

**Q：翻译失败会不会白花钱？**
译文有本地缓存，重跑同一文档的相同段落不会再请求。失败重试也有上限
（`max_retries`，默认 3 次）。

**Q：输出 PDF 里的文字能复制吗？**
能。写回的是真正的文本对象（内嵌了子集化的中文字体），不是图片。
而且做了两件事保证**复制/搜索出来的字符是对的**：

- 拉丁字符（`Vipera berus`、`Baden-Württemberg`、`2020`）走内置拉丁字体，
  不会被 CJK 字库把空格换成 NBSP、把连字符换成 `U+2010`；
- 中文字体优先选**不会把汉字提取成 CJK 兼容表意文字**的（例如 `利` 被提取成
  `U+F9DD` 就会导致搜"权利"搜不到）。这条探测（`cjk_ok`）排在字重之前，
  因为字符正确性是正确性问题、字重只是观感问题。

**Q：支持多大的文件？**
上传上限 200 MB。解析与排版都很快（几十页通常一两秒），
耗时基本取决于大模型调用；调大并发与每批段落数可以明显提速。

## 能力边界

诚实地说明当前的限制，避免误用：

- **扫描件需要先开 OCR**，且 OCR 精度受扫描质量影响很大。
- **小字 + 彩色照片背景**是最难的场景（图鉴、海报、菜单）：检测容易漏行、
  识别容易把标点认错。实测把 DPI 提到 300 后能救回大部分，但这类版面
  仍建议人工校对；普通「白底黑字」的文档扫描件效果好得多。
- **OCR 出来的文字可能有错别字**（例如 `Länge` → `Lange`、`(Hyla arborea)`
  被认成 `(Hyla arborca)`，`13.5` 被认成 `135`）。好在译文是交给大模型翻译的，
  轻微噪声通常会被模型自动纠正，但**数字、型号、人名这类关键信息请务必核对**。
- **OCR 的版面分析基于几何启发式**（行距、缩进、短行、字号变化），
  对多栏扫描件的分栏能力弱于文本层 PDF；复杂报纸版式可能段落切分不理想。
- **OCR 段落的方向**只支持 0°/180°（可选开启方向分类），不支持任意角度旋转。
- **数学公式**按普通文本处理，复杂的 LaTeX 排版公式可能不美观。
  扫描件里的公式 OCR 基本不可用，建议保留为图片。
- **两端对齐**的段落回填后按左对齐呈现（`TextWriter` 不支持两端对齐）。
- **旋转文本**（竖排 ±90°，横排表格的列标签就是这一类）单独走一条排版路径：

  - **坐标系从原文数据推出来**：起点取原文首行 span 的 `origin`，方向取行向量，
    叠放方向由相邻两行起点之差得到 —— 不去猜"该转多少度"；
  - **宽高互换**：竖排文字沿 bbox 的**高**方向排、多行沿**宽**方向叠，
    所以"一行能排多长"是 bbox 的高、"能叠几行"是 bbox 的宽。早先一律用 bbox
    的宽当折行宽度，11pt 宽的单元格会把中文折成每行 1~2 个字；旋转排版需要
    "行数 × 字号"的叠高，远超单元格宽度，于是所有字号都放不下、
    **整批回退成水平绘制** —— 实测一份 36 页文档 341 个旋转段落里 309 个朝向错乱，
    并横着压进相邻单元格。
  - **`insert_textbox` 的 `rotate` 参数与文本方向是相反数**（`rotate=90` 产出
    `dir=(0,-1)`），传错会让整列字上下颠倒。
  - 这条路径**只能用单一字体**（`insert_textbox` 的限制，没法像横排那样
    "汉字走中文字体、拉丁走内置拉丁字体"），所以要避开 ASCII 往返不干净的字库：
    等线会把 `-` 反查成 `U+2010`，实测产出里 856 处连字符在 PDF 里搜不到。
    程序会自动为竖排段落挑一个 ASCII 安全的字体。
  - **遗留限制**：`insert_textbox` 自己折行，**不适用中文避头尾**。实测 12 万字的
    译文集里因此有 54 处行首标点（0.045%），集中在极窄的竖排表头单元格里。
- **表格识别与页眉判定的冲突**：表格的表头行天然会**每页重复**、又常位于页面上方，
  形态与页眉完全一致，早先被 `skip_repeated` 判成页眉而整表列标题不翻译
  （实测一份 26 页文档漏掉 346 段，`Fläche KL` 一项被跳过 63 次）。
  现在从矢量图里识别表格区域（成组的长横线，兼容只有横线的三线表），
  落在表格里的文字**永不判为页眉页脚**，也不参与"跨页重复"统计。
- **带 `/Rotate` 的页面**（横排表格、折页常见）用**未旋转的文字坐标空间**做全部
  版面计算。这一点必须与 `page.rect` 区分开：对 `/Rotate 90` 的页面两者宽高互换，
  混用会导致行 bbox 被截断、"下方可用空间"算成 0、绘制时用错误的底边把
  页面下半部分的译文整段丢掉 —— 实测一份 36 页文档因此静默丢失 34~196 段译文。
  相关逻辑集中在 `pdf_parser.page_space()`，并有 `tests/test_lettering.py`
  的「带 /Rotate 的页面」用例守着。
- **倒排文本（180°）**（折页背面、部分双面印刷版式）会连同方向一起还原，
  译文仍竖排在同一位置，与原文的阅读方向一致。
- **双语模式**在极紧凑版面上会缩小字号；若扩展区域会压到相邻段落，则该段
  自动退化为"仅译文"（见上文）。
- **表格**里的文字会被翻译，但不会重新调整列宽 —— 如果译文比原文长很多，
  单元格内可能显得拥挤。
- **加密 PDF** 会直接报错，需要先去掉密码。部分 PDF 的**权限标记**
  （禁止修改）未做绕过处理。
- 译文**不保证逐字准确**，重要文件请务必人工校对。

## 第三方组件与致谢

本项目**没有复制任何第三方项目的源码**：全部代码为原创实现。下面写清楚
"参考了谁的什么思路"以及"用了谁的什么东西"，便于追溯与致谢。

功能设计上参考了开源社区在 PDF 翻译方向上的成熟思路：

- **[PDFMathTranslate](https://github.com/Byaidu/PDFMathTranslate)**（pdf2zh，AGPL-3.0）
  —— 提出了"解析文本块 → 翻译 → 按坐标写回"的整体思路，以及 mono（仅译文）/
  dual（双语对照）两种输出模式；本项目在此基础上做了不同的工程取舍（见下）。
- **[BabelDOC](https://github.com/funstory-ai/BabelDOC)**（AGPL-3.0）—— 字体子集化、
  按字符切换字体、以及"CJK 兼容表意文字会把 ToUnicode 反查表带偏"这类工程坑的
  公开记录。本项目在 `fonts.cjk_roundtrip_ok()` 里用**主动探测**处理同一个问题
  （写一小段字再读回来比对），探测项还包括空格与 ASCII 的往返。
- **架构分层**参考了本机另一个独立项目 Saber-Translator 的
  `app / core / interfaces / shared` 组织方式（未复制其代码，也不修改它的文件）。
- **[RapidOCR](https://github.com/RapidAI/RapidOCR)**（Apache-2.0）—— 把 PaddleOCR 的
  PP-OCR 模型转换并整理成多平台 ONNX 格式。本项目的 OCR 模型清单
  （下载 URL 与 SHA256 校验值）取自它的 `default_models.yaml`。
- **[PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR)**（Apache-2.0）—— PP-OCR
  检测/识别模型与 CTC 字符表规范的来源。**OCR 部分的代码是原创实现**：
  没有用 opencv / pyclipper，检测框聚类改用 `scipy.ndimage` 连通域，
  字符表解析也按自己的理解重写过（见 `src/core/ocr/`）。
- **MuPDF / PyMuPDF** —— 提供 PDF 解析、渲染、擦除与文本写入的全部底层能力。

与它们的主要差异是**刻意做得更轻**：不引入 ONNX / PyTorch 版面模型做版面分析，
改用纯几何启发式（覆盖投影 + XY-cut）处理有文本层的 PDF；OCR 也直接跑在
`onnxruntime` 上，不额外引入 opencv / pyclipper。因此安装体积小、启动快，
代价是在极复杂的版面上不如深度学习方案鲁棒。
